## Условие

В рамках выполнения задачи вы научитесь писать базовый код, поработаете со структурами, методами, функциями, `if`-ами, `map`-ами. Никаких дополнительных специфичных знаний вам не потребуется.
Основная цель задания — поупражняться в моделировании объектов. Когда-то давно, когда компьютеры были большими, интернет — медленным, а графических ускорителей не было вовсе, уже существовали 
многопользовательские игры. Они имели текстовый интерфейс и назывались MUD, Multi User Dungeon. Мы пишем простую игру, которая реагирует на команды игрока.

> **Подсказка:** в реализации комнат удобно использовать анонимные функции — смотрите `1/02_functions/2_firstclass/2_firstclass.go`. Также помните, что поле структуры может быть функцией.

## Устройство игры

- Игровой мир обычно состоит из комнат, где может происходить какое-то действие.
- Также у нас есть игрок.
- Как у игрока, так и у команды есть состояние.
- `initGame` делает нового игрока и задаёт ему начальное состояние.
- В данной версии можно обойтись глобальными переменными для игрока и мира (комнат).

Команда в `handleCommand` парсится как:

```bash
$команда $параметр1 $параметр2 $параметр3
```

Функция [`strings.Split`](https://golang.org/pkg/strings/#Split) вам в помощь.

## Требования к решению

В тестах представлены последовательности команд и получаемый ответ. Задача — пройти все тесты и сделать правильно. Под «правильно» понимается **универсально**, 
чтобы можно было без проблем что-то добавить или убрать. Например, добавить или убрать двери или ещё предметы, не меняя ничего в коде, кроме инита игры в `initGame`.
Но это не значит, что вам просто весь код надо затолкать в `initGame` и сделать для каждого помещения отдельную реализацию каждой из возможных команд.

### Чего делать нельзя

- Бесконечный набор захардкоженных `if`-ов для всего мира.
- Глобальная мапа с полной командой от юзера — это тоже хардкод.

Конкретные условия могут быть только внутри конкретной комнаты.

### В какую сторону думать

- Объекты, вызовы функций, структуры, которые описывают состояние комнаты и игрока, и функции, описывающие какой-то интерактив в комнате.
- Мапа из функций.
- Триггер — действие, выполняемое при каком-то событии.
- Поле структуры типа «функция».

Хардкодом (набором `if`-ов без нормального моделирования структур) это задание пишется за 3 часа. Но хардкодом нельзя! Нормально, вдумчиво — чуть дольше.

В идеале ваша архитектура с комнатами должна без проблем пережить добавление дополнительных комнат.

## Решение

Решение написано на языке **Go (Golang)** целиком в `main.go`, без сторонних библиотек (только `errors`, `fmt`, `slices`, `strings`). Главная идея: **поведение мира описывается данными, а код команд один и тот же для любого мира**. Весь мир (комнаты, двери, предметы, игрок) собирается в `initGame`, поэтому добавить комнату или предмет можно, не трогая остальной код.

### 1. Архитектура: четыре слоя

Каждая команда проходит через одну и ту же цепочку:

```text
handleCommand → CLI (Codec + Mux) → Transport → Usecase → World
```

| Слой | Типы | За что отвечает |
|------|------|-----------------|
| CLI | `CLI`, `Codec`, `Mux`, `Request`, `ResponseWriter` | Разбирает строку на команду и аргументы, находит обработчик команды |
| Transport | `LookoutTransport`, `WalkTransport`, `TakeTransport`, `PutOnTransport`, `OpenTransport` | Проверяет число аргументов, вызывает usecase, превращает результат или ошибку в текст для игрока |
| Service (usecase) | `LookoutUsecase`, `WalkUsecase`, `TakeUsecase`, `PutOnUsecase`, `OpenUsecase` | Игровая логика одной команды |
| World | `World`, `Player`, `Room`, `Item`, `Door` | Хранит состояние мира и игрока |

Такое разделение не даёт «затолкать всё в `initGame`»: логика каждой команды написана один раз и не зависит от конкретных комнат.

### 2. Модель мира

- **`World`** — игрок плюс три словаря по имени: `Items`, `Doors`, `Rooms`.
- **`Room`** — комната. Поля:
  - `Furniture` — упорядоченный срез `{Place, Items}` («на столе: ключи, конспекты»); порядок важен, чтобы вывод был детерминированным;
  - `Gateways` — выходы `{Label, Room}`: `Label` — то, что вводит игрок, `Room` — куда ведёт выход (например, выход «домой» ведёт в коридор);
  - `Door` — имя двери, которая должна быть открыта, чтобы **войти** в комнату (у улицы это `дверь`);
  - `EntryWelcome`, `LookoutWelcome`, `EmptyText` — тексты для входа, осмотра и пустой комнаты;
  - `LookoutExtra func(p *Player) string` — необязательная функция-триггер с комнатно-специфичным дополнением к осмотру.
- **`Item`** — предмет описывается набором флагов, а не кодом: `OpenDoors`, `PutOn`, `Carry`, `GivesInventory`. Ключи — `OpenDoors + Carry`, рюкзак — `PutOn + GivesInventory`, чай — без флагов (его нельзя ни взять, ни надеть).
- **`Door`** — имя и статус (открыта / закрыта).
- **`Player`** — позиция, инвентарь и одежда (множества `map[string]struct{}`), признак `InventoryAvailable` и список целей `Goals`.
- **`Goal`** — имя цели и необязательная функция `Done func(p *Player) bool`. Цель без `Done` никогда не считается выполненной («идти в универ»).

### 3. Разбор и маршрутизация команды

`handleCommand` работает по шагам:

1. `Codec.UnparseCommandString` режет строку через `strings.Fields` на команду и аргументы. Пустая строка даёт ошибку «команда не предоставлена».
2. `Mux.Process` ищет обработчик в `map[string]Handler`. Неизвестная команда даёт «неизвестная команда».
3. Создаются `Request` (команда и аргументы) и `ResponseWriter`, вызывается обработчик.
4. Если обработчик записал ошибку, возвращается её текст, иначе — сообщение.

Обработчики регистрируются в `initGame` через `cli.Handle("взять", take.Handler)` и так далее, то есть вместо глобальной мапы с полными командами или цепочки `if` используется **мапа из функций**.

### 4. Команды

| Команда | Проверки по порядку | Результат |
|---------|---------------------|-----------|
| `осмотреться` | позиция игрока существует | `LookoutWelcome`, предметы на мебели (пустая мебель пропускается; если предметов нет — `EmptyText`, а при его отсутствии «пустая <комната>»), результат `LookoutExtra`, затем «можно пройти — …» |
| `идти <куда>` | комната есть → в ней есть выход с такой меткой → целевая комната существует → если у неё есть `Door`, дверь существует и открыта | игрок перемещается, выводится `EntryWelcome` и список выходов; при любой ошибке игрок остаётся на месте |
| `взять <предмет>` | предмет существует → лежит в комнате → `Carry` → есть инвентарь | предмет убирается из комнаты и попадает в инвентарь |
| `надеть <предмет>` | предмет существует → лежит в комнате → `PutOn` | предмет убирается из комнаты и попадает в одежду; если `GivesInventory`, у игрока появляется инвентарь |
| `применить <предмет> <объект>` | предмет в инвентаре → существует → `OpenDoors` → объект — известная дверь → эта дверь ведёт из текущей комнаты | дверь открывается |

Обратите внимание, что после `надеть рюкзак` команда `взять` начинает работать: инвентарь появляется не «по имени рюкзака», а потому что у предмета стоит флаг `GivesInventory`.

### 5. Обработка ошибок

Ошибки двухуровневые:

- usecase возвращает **сервисные** ошибки на английском (`ErrServiceItemIsNotInTheRoom`, `ErrServiceDoorIsClosed` и т.д.) и ничего не знает о тексте для игрока;
- transport через `errors.Is` переводит их в **транспортные** ошибки с текстом для игрока (`ErrTransportItemIsNotInTheRoom` → «нет такого») и при необходимости дописывает контекст через `fmt.Errorf("%w: %s", …)`, например «нельзя взять: чай» или «нет пути в улица».

Так тексты сообщений можно менять, не затрагивая игровую логику.

### 6. Триггеры и цели

В кухне задан `LookoutExtra` — анонимная функция, которая собирает невыполненные цели через `Player.PendingGoals()` и добавляет к осмотру «надо собрать рюкзак и идти в универ». Как только игрок надел рюкзак, цель «собрать рюкзак» выполнена (`Done` вернул `true`), и из текста она исчезает. Так реализованы «поле структуры типа функция» и «триггер» из подсказок к заданию.

### 7. Расширяемость

Чтобы добавить комнату, достаточно описать её в `initGame` и связать с существующей выходом — код команд не меняется:

```go
balcony := &Room{
    Name:         "балкон",
    Gateways:     []Gateway{{Label: "комната", Room: "комната"}},
    EntryWelcome: "на балконе свежо",
    EmptyText:    "пустой балкон",
}
// ...и добавить её в World.Rooms, а в комнате bedroom — выход {Label: "балкон", Room: "балкон"}.
```

Аналогично добавляются двери (`Door` в `World.Doors` и поле `Door` у комнаты) и предметы (`Item` с нужными флагами, положенный на мебель).
