# Домашнее задание №4

## Условие

Это простой веб-сервис, представляющий собой менеджер MySQL-базы данных, который позволяет осуществлять CRUD-запросы (create, read, update, delete) к ней по HTTP.

В данном задании мы продолжаем отработку навыков работы с HTTP и взаимодействуем с базой данных.

> **Важно:** в этом задании нельзя использовать глобальные переменные. Всё, что нужно, храните в полях структуры, которая живёт в замыкании.

## Что видит пользователь

| Запрос | Описание |
|--------|----------|
| `GET /` | Возвращает список всех таблиц (которые можно использовать в дальнейших запросах). |
| `GET /$table?limit=5&offset=7` | Возвращает список из 5 записей (`limit`) начиная с 7-й (`offset`) из таблицы `$table`. По умолчанию `limit=5`, `offset=0`. |
| `GET /$table/$id` | Возвращает информацию о самой записи или `404`. |
| `PUT /$table` | Создаёт новую запись, данные приходят в теле запроса (POST-параметры). |
| `POST /$table/$id` | Обновляет запись, данные приходят в теле запроса (POST-параметры). |
| `DELETE /$table/$id` | Удаляет запись. |

`GET`, `PUT`, `POST`, `DELETE` — это HTTP-метод, которым был отправлен запрос.

## Особенности работы программы

- Роутинг запросов — руками, никаких внешних библиотек использовать нельзя.
- Полная динамика: при инициализации в `NewDBExplorer` считываем из базы список таблиц и полей (запросы ниже), далее работаем с ними при валидации. Никакого хардкода в виде кучи условий и написанного кода для валидации-заполнения. Если добавить третью таблицу — всё должно работать и для неё.
- Считаем, что во время работы программы список таблиц не меняется.
- Запросы придётся конструировать динамически, данные оттуда доставать тоже динамически: у вас нет фиксированного списка параметров — вы его подгружаете при инициализации.
- Валидация на уровне «string — int — float — null», без заморочек. Помните, что JSON в пустой интерфейс распаковывает числа как `float64`, если не указаны специальные опции.
- Вся работа происходит через `database/sql`, вам на вход передаётся рабочее подключение к базе. Никаких ORM и прочего.
- Все имена полей — так, как они в базе.
- В случае ошибки просто возвращаем `500` в HTTP-статусе.
- Не забывайте про SQL-инъекции. Неизвестные поля игнорируем.
- Глобальные переменные запрещены. Всё, что вы хотите хранить, храните в полях структуры, которая живёт в замыкании.

## Запросы для получения структуры БД

Эти запросы помогут получить список таблиц и их структуру:

```sql
SHOW TABLES;
SHOW FULL COLUMNS FROM `$table_name`;
```

## Подсказки

- Внутри `row`, который вы получаете из базы, лежат не только сами значения полей, но и метаданные — см. [`Rows.ColumnTypes`](https://golang.org/pkg/database/sql/#Rows.ColumnTypes).
- Тут будут активно применяться пустые интерфейсы.
- Обратите внимание на обработку `null`-значения.
- Придётся вытаскивать неизвестное количество полей из `row` — подумайте, как тут можно применить пустые интерфейсы.
- Поднять MySQL-базу локально проще всего через докер:

```bash
docker run -p 3306:3306 -v $(PWD):/docker-entrypoint-initdb.d -e MYSQL_ROOT_PASSWORD=1234 -e MYSQL_DATABASE=golang -d mysql
```

## Решение

Решение написано на языке **Go (Golang)** в файле `solution/db_explorer.go`. Используется только стандартная библиотека (`database/sql`, `net/http`, `encoding/json`, `strconv`, `strings`, `fmt`) и драйвер `github.com/go-sql-driver/mysql`, который подключён в `main.go`. Файлы `main.go` и `main_test.go` не менялись, добавлены только `go.mod` и `go.sum`.

Идея: схема базы читается один раз в `NewDBExplorer`, а дальше все запросы и проверки строятся по ней. Хардкода под конкретные таблицы нет, поэтому третья таблица заработает без изменений кода. Всё состояние лежит в структуре `explorer`, на метод которой замкнут handler, — глобальных переменных нет.

### 1. Инициализация (`NewDBExplorer`)

1. `SHOW TABLES` — список таблиц (порядок сохраняется для ответа на `GET /`).
2. Для каждой таблицы `SHOW FULL COLUMNS FROM ...` — список колонок. По каждой запоминаем: имя, тип, допустимость `NULL`, признак `PRIMARY KEY`, `AUTO_INCREMENT` и наличие значения по умолчанию.
3. `rows` закрываются сразу после чтения, иначе тест `db.Stats().OpenConnections` увидит утёкшие соединения.

SQL-тип приводится к одному из трёх видов (`kindOf`): целое (`int`, `bigint` и т. п.), дробное (`float`, `double`, `decimal`) или строка (всё остальное, включая `text`).

### 2. Роутинг (`serve`)

Путь делится на части без лишних `/` (поэтому `/items` и `/items/` равнозначны):

| Путь | Метод | Действие |
|------|-------|----------|
| `/` | `GET` | список таблиц |
| `/$table` | `GET` | список записей (`list`) |
| `/$table` | `PUT` | создание записи (`create`) |
| `/$table/$id` | `GET` | одна запись (`get`) |
| `/$table/$id` | `POST` | обновление (`update`) |
| `/$table/$id` | `DELETE` | удаление (`remove`) |

Неизвестная таблица — `404` и `{"error": "unknown table"}`. Неподходящий метод — `405`, слишком длинный путь — `404`.

### 3. Чтение записей (`list`, `get`, `query`)

- `limit` и `offset` берутся из query через `intParam`. Если значение не число, отрицательное или не передано, используется значение по умолчанию (`5` и `0`). Это же защищает от инъекций вроде `limit=1'`. В SQL они попадают только как параметры `LIMIT ? OFFSET ?`.
- `$id` сравнивается с первичным ключом таблицы через плейсхолдер. Нет записи — `404` и `{"error": "record not found"}`.
- `query` читает значения в `[]interface{}` по числу колонок из схемы, а `column.convert` приводит их к типам JSON. Драйвер отдаёт данные как `[]byte`: числовые колонки превращаются в числа, остальные — в строки, `NULL` остаётся `null`.
- Пустой результат кодируется как `[]`, а не `null`.

### 4. Создание (`create`)

- `AUTO_INCREMENT`-колонки и неизвестные поля игнорируются (поэтому `"id": 42` из теста не влияет на вставку).
- Переданные значения проверяются через `column.valid`.
- Непереданные `NOT NULL`-поля без значения по умолчанию получают нулевое значение (`""` или `0`), как в тесте, где `email` и `info` оказываются пустыми строками. Остальные пропускаются.
- Ответ: `{"response": {"<имя первичного ключа>": <новый id>}}`, например `{"id": 3}` или `{"user_id": 2}`.

### 5. Обновление и удаление (`update`, `remove`)

- В `UPDATE` попадают только известные переданные поля. Значение первичного ключа менять нельзя.
- Любое нарушение (смена ключа, неверный тип, `null` для `NOT NULL`-поля) даёт `400` и `{"error": "field X have invalid type"}`.
- Ответ на обновление: `{"updated": N}`, на удаление: `{"deleted": N}`, где `N` — число затронутых строк (повторное удаление даёт `0`).

### 6. Валидация (`column.valid`)

| Значение в JSON | Подходит, если колонка |
|-----------------|------------------------|
| `string` | строковая |
| число (`float64`) | дробная, либо целая и число целое |
| `null` | допускает `NULL` |
| всё остальное | не подходит |

JSON распаковывает любые числа в `float64`, поэтому для целых колонок проверяется, что дробной части нет.

### 7. Безопасность и ошибки

- Значения всегда передаются через плейсхолдеры `?`.
- Имена таблиц и колонок берутся только из схемы, прочитанной при старте, и дополнительно экранируются функцией `quote`. Неизвестные поля из тела запроса отбрасываются.
- Любая ошибка базы — `500` без тела. Ошибки клиента — `4xx` и JSON `{"error": "..."}`, который собирает `writeError`.
